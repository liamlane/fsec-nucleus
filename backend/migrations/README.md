# Migrations

Schema changes go here as `.sql` files. The backend runs `node-pg-migrate up` at
startup and applies any unapplied migrations before the HTTP server binds.

## Naming

`NNNN_short-description.sql` where `NNNN` is a zero-padded sequence number.
Examples:

```
0000_baseline.sql                  ← canonical starting schema (generated from live pg_dump)
0001_add_email_log.sql             ← Stage B: SMTP email integration
0002_business_recurring_billing.sql ← Stage C: recurring invoices
```

The sequence number must increase monotonically — node-pg-migrate sorts
filenames lexically and applies them in order.

## File format

```sql
-- Up Migration
ALTER TABLE foo ADD COLUMN bar TEXT;
CREATE INDEX idx_foo_bar ON foo(bar);

-- Down Migration
DROP INDEX IF EXISTS idx_foo_bar;
ALTER TABLE foo DROP COLUMN IF EXISTS bar;
```

The `-- Up Migration` marker is required. The Down section is optional but
recommended for anything reversible — you'll want it the first time something
breaks and you need to roll back.

## Creating a new migration

```bash
cd backend
npm run migrate:create -- 0001_my-change
# Creates migrations/<timestamp>_my-change.sql with the markers in place
```

Or just create the file by hand with the naming convention above.

## Applying migrations

**Production:** Automatic. Migrations run on backend container startup. Look
for `[migrate] Applied N migration(s)` in `docker compose logs backend`.

**Local development:** Either restart the backend, or run manually:

```bash
cd backend
POSTGRES_HOST=localhost POSTGRES_DB=nucleus POSTGRES_USER=nucleus \
  POSTGRES_PASSWORD=secret \
  npm run migrate up
```

## Rules

1. **Never edit a migration after it's been deployed.** Once applied, it's
   immutable history. Want to change something? Add a new migration.
2. **Never run raw SQL against the live DB for schema changes.** Always go
   through a migration file so the change is versioned and reproducible.
3. **Test locally first.** Spin up a fresh postgres container, let the
   backend apply all migrations, confirm it boots, then push.
4. **One concept per migration.** Don't combine "add a column" with "drop a
   table" — easier to debug and selectively roll back.

## The baseline migration

`0000_baseline.sql` represents the schema state at the moment Batch 6 of the
cleanup was deployed. It was generated by `pg_dump --schema-only` against the
live database. **Do not edit it.** Any schema changes from now on go in
subsequent files.

If you're spinning up a brand-new database from scratch, the baseline gets
applied automatically by the migration runner.
